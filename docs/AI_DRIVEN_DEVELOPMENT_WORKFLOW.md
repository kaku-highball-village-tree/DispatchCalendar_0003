# AI駆動開発ワークフロー

## 目的

本ドキュメントは、動画「AIを使って爆速でアプリ開発を行うためのコーディングワークフロー【バイブコーディング/AI駆動開発】」で紹介されていた開発手順を、このリポジトリで参照しやすい形に整理したものです。

DispatchCalendar は Excel、VBA、Python、Google Calendar API を扱うため、実装前の要件整理、仕様メモ、検証手順の明文化を徹底すると、AI支援コーディング時の認識ズレを減らせます。

---

## 全体フロー

1. AIとの壁打ちで要件定義を作る
2. 要件定義を Markdown として保存する
3. UIや操作フローをプロトタイプ化する
4. ローカルリポジトリへ取り込み、実装を進める
5. プロジェクトルールを整備する
6. 複雑な設計や実装結果をドキュメント化する
7. 外部サービス連携を小さく検証する
8. テストとリリース準備を行う

---

## 1. 要件定義をAIと壁打ちする

新機能を実装する前に、AIへ次の観点を質問し、要件を具体化します。

- 目的: 何を自動化・改善するのか
- 対象ユーザー: 誰が使うのか
- 入力: Excelファイル、設定ファイル、コマンド引数など
- 出力: TSV、Google Calendar イベント、エラーファイルなど
- 例外: 空欄、日付形式エラー、認証エラー、重複イベントなど
- 完了条件: どの状態になれば成功とみなすか

DispatchCalendar では、Excelの表構造やGoogle Calendar登録ルールに依存する処理が多いため、実装前に具体例を含めて整理します。

---

## 2. 要件定義をMarkdownで保存する

要件が固まったら、AIに Markdown 形式で出力させ、`docs/` 配下に保存します。

推奨ファイル例:

- `docs/requirements.md`: 機能要件
- `docs/specification.md`: 入出力仕様
- `docs/test_plan.md`: 手動・自動テスト観点
- `docs/implementation_notes.md`: 実装時の判断や注意点

保存した Markdown は、後続のAI支援作業で参照する「メモリー」や「セーブポイント」として使います。

---

## 3. UI・操作フローをプロトタイプ化する

Webアプリでは bolt.new のようなツールでUIを先に作る流れが紹介されていましたが、このリポジトリでは主に次の操作フローを先に整理します。

- Excelでマクロを実行する流れ
- Pythonスクリプトをコマンド実行する流れ
- ドラッグ&ドロップでファイルを処理する流れ
- Google認証やカレンダーID設定の流れ
- エラー発生時にユーザーへ表示・出力する流れ

画面がある場合はワイヤーフレーム、コマンドライン機能の場合は実行例と期待される標準出力・生成ファイルを明文化します。

---

## 4. ローカルリポジトリで実装する

実装時は、AIに要件ドキュメントと関連ファイルを明示してから作業します。

依頼例:

```text
@docs/requirements.md と @src/DispatchCalendar_Cmd.py を読み、
既存仕様を壊さずに〇〇機能を追加してください。
```

実装後は、必ず差分を確認し、想定外のファイル変更や不要な大規模変更がないか確認します。

---

## 5. プロジェクトルールを整備する

AI支援コーディングの精度を高めるため、リポジトリ内のルールを明文化します。

このリポジトリでは、既に `docs/VARIABLE_NAMING_RULES.md` に変数命名規則があります。新しい実装やリファクタリングを依頼する場合は、この命名規則をAIに参照させます。

追加すると便利なルール例:

- Python例外処理の方針
- Google Calendar API連携時の認証ファイル配置
- Excel列・行の扱い方
- VBAマクロの命名規則
- エラーファイル出力の統一ルール

---

## 6. 複雑な実装はドキュメント化する

次のような作業を行った後は、AIに「現在の設計をMarkdownでまとめてください」と依頼し、`docs/` に保存します。

- Excelの行結合・列補正ロジックを変更したとき
- Google Calendarイベント作成ルールを変更したとき
- 認証・トークン更新処理を変更したとき
- VBAとPythonの役割分担を変更したとき
- ユーザー操作手順を変更したとき

これにより、後から別のAIセッションで作業しても、仕様を再現しやすくなります。

---

## 7. 外部サービス連携は小さく検証する

動画では Supabase や Stripe などの外部サービス連携が紹介されていました。DispatchCalendar では Google Calendar API が主要な外部連携先です。

外部連携を変更するときは、次の順序で小さく検証します。

1. 認証ファイルとトークンの読み込みだけを確認する
2. カレンダーIDの解決だけを確認する
3. イベント作成用のデータ整形だけを確認する
4. テスト用カレンダーへ1件だけ登録する
5. 複数件登録やエラー処理を確認する

本番カレンダーに影響しないよう、検証時はテスト用カレンダーIDの使用を推奨します。

---

## 8. テストとリリース準備

変更後は、少なくとも次の確認を行います。

- Pythonファイルの構文チェック
- 代表的なExcel入力での手動確認
- エラーケースの確認
- READMEや操作手順の更新
- Git差分の確認

推奨コマンド例:

```bash
python -m py_compile src/*.py
python src/DispatchCalendar_Cmd.py --help
```

---

## AIに依頼するときのテンプレート

```text
目的:
DispatchCalendar に〇〇機能を追加したいです。

参照してほしいファイル:
- docs/VARIABLE_NAMING_RULES.md
- docs/AI_DRIVEN_DEVELOPMENT_WORKFLOW.md
- src/対象ファイル.py

守ってほしいこと:
- 既存の入出力仕様を壊さない
- 変更理由をコメントまたはドキュメントに残す
- 実装後に実行すべき確認コマンドを提示する

期待する成果物:
- コード変更
- 必要なドキュメント更新
- テスト結果の要約
```

---

## 運用メモ

AIで高速に実装する場合でも、最終的な責任はリポジトリのメンテナーが持ちます。特にカレンダー登録、認証情報、実ユーザーデータに関わる変更は、テスト用データで検証してから本番運用へ反映してください。
